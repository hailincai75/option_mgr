# FEAT-049: 使用 Google 账户登录（严格访问控制）

- **Status:** Draft
- **Priority:** P1
- **Depends on:** 无（影响全部已有接口和页面；沿用 FEAT-005 审计、FEAT-033 账户、E2E 的 `e2e` profile 与重置机制）。FEAT-050（从手机安全访问）依赖本需求
- **Scope:**
  - [ ] Backend: Done
  - [ ] Frontend: Done

## 背景 / 用户故事
目前系统没有任何身份验证：后端 localhost:8080、前端 localhost:5173（`/api` 代理），本地 H2 文件库里是真实交易数据。用户（2026-11-16）要用自己的 Gmail 账户登录，并表示要从手机经互联网访问，要求**非常严格的访问控制**。网络暴露与部署单独放在 FEAT-050；本需求是应用自身的登录，不管以后怎么部署都需要，并且在本机（localhost）就能完整使用和测试。

作为系统唯一的使用者，我想只有我的 Google 账户能登录，其它任何请求都被拒绝，以便应用暴露到网络上也不会泄露或被篡改我的交易数据。

## 已定的口径（只引用）
- Q12：审计不记录"谁"——是否改变见 Q244。Q52：E2E 重置后只剩"默认账户"。
- 只用 Google 做身份验证，不读取 Gmail、Drive 等任何其它 Google 数据；不向券商下单。

## 前提（用户自己做，agent 不做）
agent 不得创建任何账户、不得输入或保存任何凭据。由用户本人：
1. 在 Google Cloud Console 建 OAuth 2.0 客户端（"Web 应用"），同意屏幕只要邮箱信息。
2. 登记授权重定向 URI：本机一个（地址由 backend-dev 在文档中给出），以后部署时再加 FEAT-050 的主机名。
3. 把客户端 ID、密钥、允许邮箱、对外地址（规则 1）填进本地 `.env` / 环境变量。`.env` 不进 git；仓库里只许出现占位值（如 `owner@example.com`、`<client-id>`）。

## 规则
1. **登录方式**：Google OAuth 2.0 / OpenID Connect，全部由后端完成，前端不接触 token 和密钥。应用的对外地址（决定重定向 URI）是配置项：本机用 localhost，部署后改成 FEAT-050 的主机名，不改代码。
2. **允许名单**：只有名单（Q242）里的邮箱能登录；忽略大小写比较，不做其它变换（不去掉 Gmail 的点）。Google 返回的 `email_verified` 不为 true 一律拒绝。**每个请求**都按当前名单再检查一次，不在名单 → 401。
3. **默认拒绝**：后端提供的**所有**路径都要求已登录，未登录 → 401（页面请求转到登录页），响应不带任何业务数据。只有这些例外：登录页、发起 Google 登录、Google 回调、登录页需要的最小静态资源（不含应用代码）。包括：所有 `/api`、构建后的前端（规则 4）、API 文档（swagger）、actuator 等管理端点。
4. **前端由后端提供**：正式运行时，构建后的前端由后端同源提供，并受规则 3 保护——未登录拿不到应用的 JS / 页面，只能看到登录页。登录页是不含业务代码的最小页面。开发时的 Vite（5173）照常使用（不含数据，数据仍受 `/api` 保护）。
5. **会话与 cookie**：会话 cookie 为 HttpOnly、Secure、SameSite=Lax（Strict 会让 Google 回调丢失登录状态）；登录成功后换新会话 ID。空闲超时和绝对超时（从登录起算，到时必须重新登录）见 Q243，到期由服务端判定。后端重启后需要重新登录。
6. **退出登录**：服务端立即使会话失效并清除 cookie；之后旧 cookie 再用 → 401。
7. **CSRF**：所有修改数据的请求（新增、修改、删除、作废、指派、行权、行情手动值、立即刷新、退出登录等）必须带 CSRF 令牌，缺少或错误 → 403，不做任何修改。
8. **登录日志**：每次登录成功、失败、被拒绝都写一行日志：时间（UTC）、邮箱（拿得到时）、结果和原因（不在名单 / 邮箱未验证 / 用户在 Google 取消 / 其它失败）、客户端 IP。日志任何时候都不写 token、授权码、会话 ID、客户端密钥。日志只看文件（Q248）。
9. **频率限制**：登录相关路径（发起登录、回调、测试登录）按客户端 IP 限流，超过 → 429 并显示 `登录尝试过于频繁，请稍后再试`；被限流也写日志（规则 8）。阈值见 Q247，可配置。
10. **安全响应头**：所有响应带：`Content-Security-Policy`（只允许本站资源，禁止内联脚本、禁止被嵌入）、`X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`；通过 HTTPS 访问时加 `Strict-Transport-Security`。含业务数据的响应 `Cache-Control: no-store`。
11. **配置缺失**：正常运行时缺少客户端 ID、密钥、对外地址，或允许名单为空 → 行为见 Q246（PM 建议拒绝启动，日志只写缺少的变量名）。
12. **测试专用登录**：自动化测试**绝不**连接真实 Google。测试登录：给定邮箱和 `email_verified`，模拟"Google 返回了它"，之后走与真实登录**相同**的名单、会话、超时、CSRF、限流、日志规则。只在 `e2e` profile（已强制内存库）和后端测试中存在；任何其它 profile 下该入口**不存在**（404），且不能靠单独一个配置开关在文件库上打开。测试环境的允许名单用虚构邮箱（`owner@example.com`），可进 git；测试环境可把超时配置得很短。
13. **后台任务不受影响**：定时行情拉取、16:20 收盘快照、临时休市检测照常运行，不需要有人登录。
14. **数据不变**：不加用户表、不迁移、不按用户隔离数据（Q245）。

## 需要的数据和操作（给 backend）
- 发起 Google 登录、处理回调（规则 1、2）；退出登录（规则 6）；查询当前用户（返回邮箱，未登录 401）；前端获取 CSRF 令牌的方式（规则 7）。
- 统一的 401 / 403 / 429 错误格式；被拒绝时把原因和邮箱交给登录页显示。
- 规则 3–5、8–11 的保护、日志、限流、响应头、超时；正式运行时同源提供前端（规则 4）。
- 测试专用登录（规则 12）。配置项：客户端 ID、密钥、允许名单、对外地址、超时、限流阈值，从环境变量 / `.env` 读取。
- 已有全部接口的业务行为不变。

## 页面与交互（给 frontend）
- **登录页**（规则 4，最小页面）：系统名称 + 按钮 `使用 Google 登录`；需要时在按钮上方显示提示：`该 Google 账户（<邮箱>）无权使用本系统`、`登录已过期，请重新登录`、`登录尝试过于频繁，请稍后再试`。不显示业务数据。
- **顶部栏**：账户切换器旁显示当前邮箱和 `退出登录`（不弹确认）。
- **全局处理**：任何请求 401 → 登录页（`登录已过期，请重新登录`），未提交的表单内容不保留；登录后回到原来的页面（含查询参数，如 `?account=2`）。所有写请求自动带 CSRF 令牌。
- 手机浏览器上登录页和顶部栏可正常使用（其余页面的手机适配不在本需求）。

## 验收标准
场景（所有条目共用）：E2E 环境，允许名单 = `owner@example.com`，测试配置空闲超时 2 分钟、绝对超时 5 分钟、登录限流每 IP 每分钟 10 次；重置后"默认账户"已入金 10,000.00（2026-11-16 10:00）。"登录为 X"指通过规则 12 的测试登录。

1. **默认拒绝**：**Given** 未登录 **When** 打开 `/positions` **Then** 只显示登录页和 `使用 Google 登录`，页面无任何金额；**When** 请求账户列表、持仓、资金接口、前端应用的 JS 文件、API 文档、actuator **Then** 都是 401 或转到登录页，响应中没有 `10,000.00`、账户名或应用代码。
2. **允许的邮箱**：**Given** 未登录时打开过 `/cash?account=1` **When** 登录为 `Owner@Example.COM` **Then** 回到该页，总现金 `10,000.00`，顶部显示邮箱和 `退出登录`；日志有一行成功记录，不含 token / 会话 ID。
3. **不在名单 / 未验证**：**When** 登录为 `intruder@example.com` **Then** 登录页显示 `该 Google 账户（intruder@example.com）无权使用本系统`，资金接口仍 401，日志记一行"不在名单"；**When** 登录为 `owner@example.com` 但 `email_verified` = false **Then** 同样被拒绝，日志原因"邮箱未验证"。
4. **CSRF**：**Given** 已登录 **When** 不带 CSRF 令牌提交入金 500.00 **Then** 403，总现金仍 `10,000.00`、流水无新记录；**When** 在资金页正常录入入金 500.00 **Then** 总现金 `10,500.00`。
5. **退出登录**：**Given** 已登录 **When** 点 `退出登录` **Then** 显示登录页；后退或再开 `/positions` 仍是登录页；用退出前的 cookie 请求资金接口 → 401。
6. **空闲超时**：**Given** 已登录并打开入金表单 **When** 2 分钟无请求后提交入金 500.00 **Then** 转到登录页并显示 `登录已过期，请重新登录`；重新登录后总现金仍 `10,000.00`。
7. **绝对超时**：**Given** 登录后每 1 分钟刷新一次页面 **When** 登录满 5 分钟后的下一次请求 **Then** 401，转到登录页。
8. **频率限制**：**When** 同一 IP 在 1 分钟内第 11 次发起登录 **Then** 429，登录页显示 `登录尝试过于频繁，请稍后再试`，日志记一行；1 分钟后可以再登录。
9. **cookie 与响应头**：**Given** 已登录 **Then** 会话 cookie 带 HttpOnly、Secure、SameSite=Lax；任一页面和接口响应带规则 10 的响应头，业务接口带 `Cache-Control: no-store`；登录前后会话 ID 不同。
10. **测试登录只在测试环境 / 回归**：**When** 不带 `e2e` profile 启动（配置齐全）**Then** 测试登录和测试重置入口都是 404；**When** 缺少允许名单启动 **Then** 按 Q246 处理（建议：启动失败，日志只写变量名）。`gradlew.bat build` 和全量 E2E（现有约 435 个 + 本需求）全部通过，已有测试只增加"先登录 / 带 CSRF"，不删减原断言。

## 手动验收（用户本人做，不计入自动化测试）
完成前提后在本机：点 `使用 Google 登录` → Google → 回到系统显示自己的邮箱；用不在名单里的 Google 账户 → 显示拒绝提示，日志有记录。

## 边界情况
- **多个标签页**：共用会话；一个标签页退出后，另一个下次请求 → 登录页。
- **在 Google 页面取消**：回到登录页，不建立会话，日志记"用户取消"。
- **改允许名单**：改配置后重启生效；重启本身也使全部会话失效（规则 5）。
- **全部账户模式、账户切换器**：登录后照常，与邮箱无关。
- **离线 / Google 不可用**：不能新登录，已有会话到期前照常可用（Q249）。
- **伪造来源 IP**：限流和日志用的客户端 IP 只信任本机反向代理给出的头（FEAT-050 定代理）；直接访问时用连接地址。

## Out of Scope
- 网络暴露、HTTPS 证书、部署主机、备份（FEAT-050）。
- 多用户数据隔离、用户管理页面、角色权限；用户名 / 密码登录、其它身份提供方、应用内两步验证（交给 Google 账户）。
- 读取任何 Google 数据；在页面上查看登录日志（Q248）；审计记录加邮箱（除非 Q244 决定要）。
- 除登录页、顶部栏以外页面的手机适配。

## Open Questions
- **Q242 允许名单**：只允许 1 个邮箱还是多个？PM 建议：配置格式支持多个，但现在只填你自己 1 个；多个邮箱看到同一份数据。
- **Q243 会话时长**：空闲超时、绝对超时各多长？PM 建议：空闲 30 分钟、绝对 12 小时；代价是手机上每天至少重新点一次登录（手机已登录 Google 时只需一两下）。
- **Q244 审计记邮箱**：审计记录要不要开始记"谁"？PM 建议：不加（Q12 不变），只有一个使用者；谁登录过由规则 8 的日志回答。
- **Q245 已有数据**：确认不迁移、不加用户字段，登录后原样可见。PM 建议：是。
- **Q246 配置缺失**：拒绝启动，还是不带登录照常运行并警告？PM 建议：拒绝启动，避免忘配 `.env` 时数据裸露。
- **Q247 限流阈值**：PM 建议每 IP 每分钟 10 次、所有 IP 合计每分钟 30 次，超过后 1 分钟内一律 429；只有你一个人用，正常不会碰到。
- **Q248 登录日志怎么看**：只写日志文件，还是应用里加一页"最近登录"？PM 建议：先只写文件（保留 90 天）；想在手机上看时另立小需求。
- **Q249 备用登录**：连不上 Google 时要不要本地密码等备用方式？PM 建议：不要，多一种方式就多一个攻击面；代价是 Google 故障时暂时进不去。
