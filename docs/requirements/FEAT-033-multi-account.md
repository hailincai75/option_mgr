## 背景 / 用户故事
作为一个期权交易者，我实际有 2 个券商账户在做期权交易。我想要在系统里分别为每个账户记账：每个账户有自己的现金、冻结、交易、持仓、已实现盈亏和审计记录，互不影响。并且我已经在用 M1 记录真实数据，**升级后这些数据必须原封不动地出现在一个默认账户里**，数字一分不差，审计历史一条不少。

这是 M1.5 的第一步。本需求只做"分账户记账"：每次只看、只写一个账户。"全部账户"合并查看在 FEAT-035，账户间转账在 FEAT-036，归档/删除在 FEAT-037。

## 已定的口径
- 推翻 Q3（单账户）：支持多个账户（用户在 M1 完成后的新决定，见 backlog Q3）
- 只有 USD（Q4）；所有 M1 规则不变（Q6、Q7、Q13、Q16–Q29、Q36、Q39、Q41、Q45 等），只是**作用范围从"整个系统"变为"每个账户"**
- 本系统只做管理与分析，不下单；CLAUDE.md 禁止提交任何账号和真实交易数据

- 账户只记名称和可选券商备注，不记账号（Q51）
- 已有数据迁入名为"默认账户"的账户；空库也自动有一个"默认账户"（Q52）
- 所有规则按账户独立（Q53）
- 记录不能改到另一个账户，录错请删除后在正确账户重录（Q54）
- 顶部全局账户切换器，记住上次选择（Q55）
- 本需求不做合并查看（Q56）、账户间转账（Q57）、删除和归档（Q58）
- 账户新增、改名写审计（Q59）
- 升级时自动备份数据库文件（Q60）

## 需要的数据和操作（给 backend）

### 账户
| 字段 | 规则 |
|------|------|
| 账户 ID | 系统生成 |
| 名称 | 必填；去首尾空格后 1–30 个字符；**不区分大小写唯一**（`主账户` 与 ` 主账户 ` 重复；`Main` 与 `main` 重复） |
| 券商备注 | 可选，≤ 50 字符，自由文字（如 `IBKR`）。**不是账号字段**，不做任何账号格式处理 |
| 创建时间 | 服务器时间 |

操作：
- 列出全部账户（按 ID 升序）。
- 新增账户（名称、券商备注）。
- 修改账户（名称、券商备注）。
- 不提供删除（Q58）。
- 新增、修改各写一条审计记录（Q59）：对象类型"账户"，内容为名称和券商备注；记在该账户自己的审计里。

### 按账户隔离（Q53）
以下数据都属于且只属于一个账户：入金/出金、现金流水、期权交易（开仓、平仓）、审计记录。下列计算全部**只在同一账户内**进行：
- 总现金 / 冻结 / 可用；Q19 按时间重放；Q18 STO put 担保；BTC 先释放冻结再检查（Q20）
- 持仓、Q7 多空冲突、Q23 multiplier 一致、Q21 FIFO 整笔平仓、被平批次匹配和补录后的重新匹配（Q27、Q39）
- 已实现盈亏、已平仓记录、盈亏汇总、首页概览（FEAT-006、FEAT-008）
- 修改/删除时的整体重放检查（FEAT-005）

同一合约在不同账户里是互不相干的两个持仓（例：A 账户空头、B 账户多头是允许的）。

所有现有的读写操作都要求指明账户（如何传递由 backend 写进契约）：
- 写操作（入金/出金、开仓、平仓、修改、删除）写入或修改指定账户的数据；记录不属于该账户时按"不存在"处理。
- 读操作（现金汇总、流水、交易列表、按 ID 查询、持仓、已平仓、盈亏汇总、首页概览、审计记录）只返回指定账户的数据。
- 指定的账户不存在 → 返回明确的错误，不返回任何数据。
- 记录的账户不能被修改（Q54）。

### 已有数据迁移（真实数据，重点）
升级到本版本时，数据库中已有的全部数据必须安全迁入一个默认账户：

1. 新建账户：ID 为最小 ID（1），名称"默认账户"，券商备注为空（Q52）。
2. **所有**已有记录归入该账户：入金/出金、现金流水、期权交易、审计记录。
3. **不改动任何已有记录的内容和 ID**：交易 ID、入金/出金 ID、流水 ID（录入顺序）、审计 ID、时间、金额、冻结变动、备注、审计的修改前/修改后内容和连带变化全部保持原值。
4. 迁移后，在默认账户下看到的**每一个数字和列表都与升级前完全相同**：现金汇总、流水（含每条余额）、交易列表、持仓（含批次、DTE）、已平仓记录（含被平批次和盈亏）、盈亏汇总、首页概览、审计记录。
5. 迁移要么完整成功，要么不改变数据库（失败时应用不启动，并给出清楚的日志）；不允许出现"一部分记录有账户、一部分没有"的状态。
6. **升级前自动备份（Q60）**：应用启动时如果发现有待执行的数据库迁移，且使用的是本地文件数据库，先把数据库文件复制一份到 `data/` 下带时间戳的备份文件，再执行迁移；备份失败则不迁移、不启动。（`data/` 不进 git。）内存数据库（测试、E2E）不备份。
7. 空库（新装）迁移完成后同样只有一个"默认账户"、没有任何数据；E2E 的重置接口恢复到这个状态。

### 审计记录的扩展
- 审计对象类型增加"账户"（新增 / 修改）。
- 审计记录属于账户：期权交易、入金/出金的审计归该记录所在账户；账户的审计归该账户本身。

## 页面与交互（给 frontend）

### 账户切换器（Q55）
- 页面顶部（导航栏）一个全局账户切换器，显示当前账户名称，下拉列出全部账户。
- 所有页面（首页、资金、录入交易、交易列表、持仓、已平仓、盈亏汇总、审计记录）都只显示和只写**当前账户**的数据；页面标题或醒目位置显示当前账户名（如"当前账户：小账户"），避免录错账户。
- 切换账户后当前页面立即显示新账户的数据，不需要刷新；打开着的录入/修改对话框以打开时的账户为准（切换时关闭或提示）。
- 记住上次选择的账户（浏览器本地）；第一次打开或记住的账户已不存在时，选 ID 最小的账户。
- 地址栏里已有的筛选参数（FEAT-002/006/008 等）不带账户，按当前账户解释。
- 只有一个账户时切换器也显示（显示该账户名）。

### 账户管理页
- 新增"账户"页面（导航入口，可放在切换器下拉的"管理账户"里）。
- 列表：名称、券商备注（空为 `—`）、创建时间（美东）。
- "新增账户"：名称、券商备注；表单提示"请勿填写账号"。成功后新账户出现在切换器中（不自动切换，或询问是否切换，由 frontend 定）。
- 每行"修改"：改名称、券商备注。
- 名称为空、超过 30 字符、与已有账户重名 → 错误显示在名称字段下。
- 没有删除按钮。

### 其它
- 所有现有页面的行为、数字、testid 保持不变（只是范围变成当前账户），M1 的前端测试和 E2E 在"默认账户"下应全部继续通过。
- 任何写操作成功后的刷新与 M1 相同；切换账户时所有查询按新账户重新获取。

## 边界情况
- **同一合约跨账户**：两个独立持仓，可以一多一空（验收 7）；平仓只匹配本账户的批次。
- **同一时间的记录**：录入顺序在账户内部比较；ID 仍是全局递增的数字，账户之间互不影响排序结果。
- **记录录错账户**：不能改账户，删除后重录（Q54），两边各有审计。
- **账户重名**：不区分大小写、去首尾空格后比较（验收 4）。
- **只有一个账户**：行为与 M1 完全相同。
- **切换账户时有打开的对话框**：以打开时的账户为准，或关闭对话框（frontend 定，但不能把记录写进切换后的账户而用户不知情）。
- **迁移**：已有 ID、录入顺序、审计内容全部保留；失败不留半成品（验收 1、2）。
- **升级备份**：文件数据库才备份；备份在 `data/`，不进 git。
- **周末 / 假日、拆股**：与 M1 相同，不在本需求。

## Implementation Notes
### Backend
**API**（详见 `docs/api/api-contract.md` 的 FEAT-033 小节；**不兼容变更**）
- 账户通过请求头 **`X-Account-Id: <账户 id>`** 指明。除 `/api/health`、`/api/accounts/**`、`/api/test-support/**` 外的**所有**接口都必须带：没带 → 400 `ACCOUNT_REQUIRED`（`details[].field = "X-Account-Id"`）；不是整数 → 400 `BAD_REQUEST`；账户不存在 → 404 `ACCOUNT_NOT_FOUND`。路径、query 参数、请求体、响应体都不变。前端：在统一请求封装里按当前账户加这个头；TanStack Query key 带上账户 id

**设计决定**
- **请求头而不是路径前缀**：已有路径、地址栏筛选参数都不变（Q55 要求链接不带账户），前端只改一处请求封装；缺头时**拒绝而不是默认账户 1**——需求要求"所有读写操作都要求指明账户"，默认值会让漏带头的写操作悄悄落进默认账户（需求最担心的"录错账户"）
- 迁移：`account` 表 + 账户 1"默认账户"；4 张数据表 `ADD COLUMN account_id BIGINT DEFAULT 1 NOT NULL`（已有行 = 1），再去掉默认值，加外键和索引；`cash_account` 的 1 号行成为默认账户的锁行；审计表放开 `before_json`、扩展两个 CHECK 约束。**不改任何已有行的内容和 id**
- 名称唯一：`name_key`（去空白 + `toLowerCase(Locale.ROOT)`）上的唯一约束
- Q60 备份用 H2 `BACKUP TO`（数据库打开时也一致），文件放在数据库文件所在目录（开发时即 `backend/data/`），名为 `optionmgr-backup-before-V5-<UTC yyyyMMdd-HHmmss>Z.zip`；只对"已有迁移记录且有待执行迁移的文件库"做，内存库和全新的库不做；备份失败 → 不迁移、应用不启动
- 全有或全无：H2 的每条 DDL 都会单独提交，Flyway 无法把 V5 整体回滚。所以"失败不留半成品"靠**迁移前的备份**保证：迁移失败时应用不启动（日志说明原因），用备份 zip 恢复即回到迁移前（`MigrationFromM1Test` 模拟了迁移失败和备份失败两种情况）。恢复步骤见下
- 账户新增：同一事务里建账户、建 `cash_account` 锁行、写 `CREATE` 审计

**已知限制**
- 迁移中途失败时数据库可能停在部分迁移的状态（H2 DDL 不可回滚），必须用备份恢复（见下）
- 并发创建同名账户时由数据库唯一约束兜底，第二个请求会得到 500 而不是 `账户名称已存在`（单用户，几乎不会发生）
