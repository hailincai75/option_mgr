## 背景 / 用户故事
用户在券商对同一合约的两笔空头 call 批次中，买入平仓（BTC 1 张）的是**较晚**的那笔，较早的那笔还持有。本系统平仓永远平掉最早的批次（FIFO 整笔，Q21），记进来后已实现盈亏和剩余批次都与券商不一致。用户原话："在你的平仓界面里面会平哪个？我需要能够选择"。

作为一个期权交易者，我想要平仓时自己选平掉哪一笔或几笔开仓批次（默认仍是 FIFO），以便已实现盈亏、剩余批次、冻结现金和券商一致。

## 已定的口径（沿用）
- 只能整笔平掉批次，不支持部分平仓一笔批次（Q21 的"整笔"部分不变）
- 净额含手续费（Q6）；BTC 平空头 put 先释放被平批次冻结、再检查现金（Q20）；Q19 重放；Q36 / Q83 时间限制；multiplier 取持仓（Q23）
- 已实现盈亏按整笔平仓计算（Q21 公式不变，只是"被平批次"改为"所选批次"）
- 修改 / 删除写审计（Q12、Q44）；可改字段 Q43 加"被平批次"（Q256）
- Q255：每笔平仓固定保存所选批次，取消 Q39 的重新匹配；Q256：可修改所选批次；Q257：录入交易页仍按张数 FIFO；Q258：批次列表字段与默认；Q259 / Q260：股票卖出、指派 / 行权不选批次
- 全部账户只读（FEAT-035）；所有规则按账户独立（Q53）

**规则变更：** Q21 已修订为"默认 FIFO、可指定任意整笔批次"，Q39 已被 Q255 取消；CLAUDE.md 领域规则已同步。

## 规则
1. **所选批次**：一笔平仓（BTC / STC）指定被平掉的 1 笔或多笔开仓批次，可以不连续（如只选第 2 笔）。每个所选批次必须：属于同一账户、同一合约；在本笔成交时点已开仓（同一时间按录入顺序，Q19）且尚未被其它平仓 / 作废 / 被指派 / 行权平掉；不能重复。至少选 1 笔。
2. **张数 = 所选批次张数之和**，不另行输入；不能部分平掉一笔批次。
3. **默认 FIFO**：表单默认选中最早的 1 笔批次（等于原来"可平张数"最小值时的结果）。用户不改选择时，结果与现在完全相同。
4. **跟随所选批次计算**：已实现盈亏（Q21 公式）、BTC 平空头 put 释放的冻结（所选批次冻结之和，Q20）、剩余批次、FEAT-039 被覆盖股数的释放（所选批次中受检批次的股数；"未覆盖"的旧批次释放 0，Q79）、FEAT-048 剩余批次的未实现盈亏。
5. **保存所选批次**：平仓记录保存它平掉的批次；之后任何重放（补录、修改、删除，FEAT-005 / Q39）都用保存的批次，不再按 FIFO 重新匹配。重放时任一平仓的所选批次不满足规则 1（如被删除、开仓时间改到平仓之后、已被更早的平仓选走、张数被改）→ 拒绝本次保存，提示中指出是哪笔平仓、哪笔批次（例："2026-11-19 10:00 BTC 1 张 ZZQ 2026-12-18 9 C 选中的批次 2026-11-11 10:00 STO 1 张 已被更早的平仓平掉"）。已有平仓与补录的处理见 Q255。
6. **已有数据**：本需求上线前录入的平仓，被平批次保持现在推导出的结果，已实现盈亏、现金、冻结、持仓、已平仓记录全部不变（存储方式见 Q255）。
7. **其它事件不变**：到期作废（Q65 全部剩余张数）、被指派（Q73）、行权（Q112）仍按最早整批次（Q260）；股票卖出与 call 被指派交股仍按股票 FIFO（Q69 / Q87，Q259）。它们作用在"所选批次平掉之后剩下的批次"上。

## 需要的数据和操作（给 backend）
- **持仓的批次列表**（平仓表单用）：每个仍持有批次的开仓交易标识、开仓时间、张数、开仓净额（带现金方向符号）、冻结（空头 put）、未实现盈亏（FEAT-048 已有，按 Q258）；按开仓时间升序；标出默认选中的批次（规则 3）。
- **新增平仓**：请求里带所选批次（规则 1、2）；校验顺序沿用 FEAT-004（所选批次校验放在原"张数"那一步），失败返回可直接显示的中文原因，例：
  - 未选批次："请至少选择一笔开仓批次"
  - 批次在成交时尚未开仓："所选批次（2026-11-11 10:00 STO 1 张）在成交时间 2026-11-10 15:00 还未开仓"
  - 批次已被平掉 / 不属于本账户本合约 / 重复：说明哪一笔
  - 如果请求同时带张数且 ≠ 所选批次之和：拒绝（由 backend 在契约中决定请求是否带张数）
- **修改平仓**（Q256）：可改所选批次（张数随之变），同样按规则 1、5 校验和重放；审计记录的修改前 / 修改后内容包含所选批次。修改表单需要"本笔平仓成交时点可选的批次"（排除本笔自身占用后）。
- **按 ID 查询、交易列表、已平仓记录**：被平批次 = 保存的所选批次（FEAT-004 / 006 的字段不变）。
- **录入交易页的 BTC / STC**（Q257）：保持现有的"按张数、FIFO 最早整批次"方式，保存时把匹配到的批次存为所选批次。
- **已有数据迁移**（规则 6、Q255）：迁移前后每笔平仓的被平批次、已实现盈亏、现金流水、冻结、持仓完全一致，ID 不变。

## 验收标准
当前时间不早于 2026-11-20 10:00（美东）。ZZQ 是虚构标的，甲 / 乙是虚构账户。"现金汇总" = 总现金 / 冻结 / 可用。

**场景 Z（账户甲，空头 call）：** 入金 1,000.00（2026-11-01 10:00）；转入 200 股 ZZQ，成本 1,600.00（2026-11-02）；A = STO 1 张 ZZQ 2026-12-18 9 C 净额 18.34（2026-11-10 10:00）；B = STO 1 张同合约 净额 37.34（2026-11-11 10:00）。现金汇总 1,055.68 / 0.00 / 1,055.68；ZZQ 股票 200 股、被覆盖 200、可用 0。

**场景 P（账户甲，空头 put）：** 入金 30,000.00（2026-11-01 10:00）；P1 = STO 2 张 ZZQ 2026-12-18 8 P 净额 30.00（2026-11-10 10:00，冻结 1,600.00）；P2 = STO 1 张同合约 净额 21.00（2026-11-11 10:00，冻结 800.00）。现金汇总 30,051.00 / 2,400.00 / 27,651.00。

1. **表单列出批次、默认 FIFO**
   **Given** 场景 Z **When** 点 ZZQ 2026-12-18 9 C 行的"平仓" **Then** 批次列表 2 行，从上到下 `2026-11-10 10:00 STO 1 张 +18.34`（已勾选，标"FIFO 默认"）、`2026-11-11 10:00 STO 1 张 +37.34`（未勾选）；显示"平仓张数：1"；方向 `BTC（买入平仓）`。

2. **选较晚的批次平仓（用户的真实情况）**
   **Given** 场景 Z **When** 取消 A、勾选 B，净额 15.10，成交时间 2026-11-19 10:00 提交 **Then** 保存成功；确认信息被平批次只有 `2026-11-11 10:00 STO 1 张 +37.34`，已实现盈亏 `+22.24`；现金汇总 1,040.58 / 0.00 / 1,040.58。
   **And** 持仓页该合约空头 1 张，唯一批次为 A（`2026-11-10 10:00`、`+18.34`）；ZZQ 股票被覆盖 100、可用 100。
   **And** 已平仓页该行开仓净额合计 `+37.34`、盈亏 `+22.24`，展开为批次 B；按 ID 查询的被平批次为 B。

3. **不改默认时与现在相同**
   **Given** 场景 Z **When** 不改勾选，净额 15.10，成交时间 2026-11-19 10:00 提交 **Then** 被平批次为 A，已实现盈亏 `+3.24`；剩余批次 B `+37.34`；现金汇总 1,040.58 / 0.00 / 1,040.58。

4. **空头 put：只平较晚的 1 张批次，释放该批次冻结**
   **Given** 场景 P **When** 只勾选 P2（平仓张数 1），BTC 净额 9.65，成交时间 2026-11-19 10:00 **Then** 保存成功；冻结变动 `−800.00`，已实现盈亏 `+11.35`；现金汇总 30,041.35 / 1,600.00 / 28,441.35；剩余批次 P1 2 张 `+30.00`、冻结 1,600.00。
   **And**（另起场景 P）勾选 P1 和 P2（平仓张数 3），净额 20.00 **Then** 冻结变动 `−2,400.00`，已实现盈亏 `+31.00`，现金汇总 30,031.00 / 0.00 / 30,031.00，持仓中没有该合约。

5. **所选批次校验（后端，每项都不保存、现金和持仓不变）**
   **Given** 场景 Z；账户乙另有 C = STO 1 张 ZZQ 2026-12-18 9 C（乙有 100 股 ZZQ）
   - **When** 在甲录入 BTC、成交时间 2026-11-10 15:00、选 B **Then** 拒绝，提示"所选批次（2026-11-11 10:00 STO 1 张）在成交时间 2026-11-10 15:00 还未开仓"。
   - **When** 不选任何批次 **Then** 前端提交按钮不可用；直接调用后端也被拒绝"请至少选择一笔开仓批次"。
   - **When** 在甲选乙的批次 C，或同一批次选两次 **Then** 拒绝并指出该批次。
   - **When** 第 2 条之后再录 BTC 选 B **Then** 拒绝，提示 B 已被平掉。

6. **重放使用保存的批次（规则 5）**
   **Given** 第 2 条完成后（B 已被 2026-11-19 10:00 的 BTC 选中）
   - **When** 把 B 的成交时间改为 2026-11-19 11:00，或删除 B **Then** 拒绝，提示指出 2026-11-19 10:00 那笔 BTC 和批次 B；数据不变。
   - **When** 补录 BTC 1 张、成交时间 2026-11-15 10:00、选 B **Then** 拒绝（B 已被之后的平仓选中，提示同规则 5 例子）；改选 A、净额 10.00 **Then** 保存成功，已实现盈亏 `+8.34`，2026-11-19 那笔仍是 B、盈亏仍 `+22.24`，持仓中没有该合约，现金汇总 1,030.58 / 0.00 / 1,030.58。

7. **修改已有平仓的所选批次（Q256）**
   **Given** 第 3 条完成后（按 FIFO 平掉了 A）**When** 在交易列表修改这笔 BTC，改为只勾选 B，其余不变 **Then** 保存成功；已实现盈亏变为 `+22.24`，剩余批次为 A `+18.34`，现金汇总不变（1,040.58 / 0.00 / 1,040.58）；审计记录一条"修改"，修改前被平批次 `2026-11-10 10:00 1 张`、修改后 `2026-11-11 10:00 1 张`。
   **And**（场景 P 中第 4 条第一种平仓之后）把所选批次从 P2 改为 P1 **Then** 张数变为 2，冻结变动变为 `−1,600.00`，已实现盈亏 `+20.35`，现金汇总 30,041.35 / 800.00 / 29,241.35。

8. **已有数据不变（规则 6）**
   **Given** 上线前用旧版本录入的数据：FEAT-004 场景 A 加一笔 BTC 2 张 净额 241.30（2026-11-05 10:00，平掉 L1，盈亏 +457.40）**When** 升级后查看 **Then** 该平仓被平批次仍为 L1、盈亏 `+457.40`，现金汇总 80,817.40 / 20,000.00 / 60,817.40，持仓剩 L2 1 张，流水与 ID 不变。

9. **录入交易页与全部账户**
   **Given** 场景 Z **When** 在录入交易页录入 BTC 1 张（不选批次）**Then** 按 FIFO 平掉 A，结果同第 3 条（Q257）。
   **Given** 第 2 条完成后切换到"全部账户" **Then** 持仓页没有"平仓"按钮；已平仓页该行展开为批次 B，账户列为甲。

## 边界情况
- **不连续选择**：可只选中间或较晚的批次（第 2、4 条）。
- **一笔平仓选多个批次**：盈亏整笔计算（第 4 条）。
- **同一时间的开仓与平仓**：按录入顺序，先录入的开仓才能被同一时间后录入的平仓选中（规则 1）。
- **到期日当天 / 之后**：Q36 / Q83 不变。
- **covered call 覆盖**：释放跟随所选批次（规则 4）；同时有"未覆盖"旧批次和受检批次时，选哪一笔就释放哪一笔的覆盖股数。
- **股票数量检查**：重放时 FEAT-039 的"任何时点持股 ≥ 被覆盖股数"仍要满足，选择不同批次可能让后面的股票卖出变得合法或不合法，按 Q19 重放判定。
- **之后的作废 / 被指派 / 行权**：只作用于剩余批次（规则 7）。例：第 2 条之后 A 被指派 1 张，指派的是 A。
- **批次被修改的开仓**：张数、时间、删除都可能让引用它的平仓失效 → 拒绝（第 6 条）；只改开仓净额 / 备注允许，所选平仓的盈亏随之变化。
- **旧审计记录**：本需求之前的平仓审计内容没有所选批次，原样显示，不补写。
- **拆股、周末假日**：不涉及。
- **受影响的已有测试（给 QA 参考）**：依赖 Q39"补录后之后的平仓重新匹配"的用例（FEAT-004 验收 10、FEAT-006 对应用例）按 Q255 结果改变；持仓页平仓对话框的张数单选被批次列表取代。

- **领域**（`trade/domain`）：`LotTrade.lotTradeIds`（BTC / STC 的所选批次，null = FIFO）；`ContractReplay` 带批次的平仓按"持仓 / 方向 → 所选批次逐个（未开仓 / 已被平掉 / 张数不符）"检查并移除正好这些批次，违规为新 `ViolationKind.CLOSE_LOTS_INVALID`，细节在 `ReplayedTrade.lotProblems`（新 `LotProblem`）；`ReplayedTrade.lotsBefore`；`TradeRejectionMessages` 新文案（a–e、之后平仓违规、删除被选中开仓）。
- **服务**：`CloseLotStore` + `OptionCloseLotEntity` / `OptionCloseLotRepository`；`OptionTradeService.close` 支持 `lotTradeIds`（检查顺序 位置/方向 → a–e → 之后记录 → 现金），两种模式都保存匹配到的批次；`closeLotChoices`（新端点）；`load` / `toLotTrade`、`OptionPositionService`、`CoverageService` 读入保存的批次。`OptionTradeEditService`：平仓可改 `lotTradeIds`（张数 = 批次之和，`NO_CHANGES` 按集合比较），开仓 `contracts` 必填改为服务层校验；删除被选中开仓 → `CLOSE_LOTS_INVALID`；删除平仓先删其批次行；审计 `before` / `after` 的 `selectedLots` 与 `changes` 首项"被平批次"。
- **Web**：`CloseTradeRequest` / `EditTradeRequest` 加 `lotTradeIds`（`@LotSelection` 类级校验：空数组、null / ≤0、>1000、FIFO 缺张数；元素须为 JSON 整数，否则 `BAD_REQUEST`）；`GET /api/option-trades/{id}/close-lot-choices`；持仓 `lots[].closeDefault`；`ErrorCode.CLOSE_LOTS_INVALID`。
- **设计决定**（契约阶段 6 条均按所写）：FIFO 模式严格按最早整批次（不跳过之后平仓已选的批次，选到了在第 4 步拒绝）；`[]` 与不带区分；EXP / ASG / EXR 不存批次；修改表单的可选批次不带未实现盈亏；检查顺序按契约；V18 不一致即失败。删除被选中的开仓按重放顺序报告（所以更早的作废 / 指派违规先报）。`CONTRACTS_MISMATCH` 在修改开仓时指向被修改的那笔开仓。
